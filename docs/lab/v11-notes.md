## 2. ★ 꼭 이해하고 갈 것

### (A) canary — 모호하지 않은 증거
- `WSCANARY-config-1a2b` 같은 무작위 토큰을 실험용 파일에 심는다.
- 보통 문장(`return 0;`)은 아무 파일에나 있지만, 무작위 토큰은 그 파일에만 있다.
- 그래서 요청 body 에 그 토큰이 있으면 "그 파일의 바이트가 이 요청에 있었다" 는 말에 다른 해석이 없다.
- 반대로 "못 본 canary" 는 **캡처된 body 안에서는** 안 보였다는 뜻까지만이다.

### (B) 줄 run — canary 없는 일반 파일
1. body 를 JSON 으로 파싱해서 문자열 값마다 view 를 만든다. 파일 내용은 보통 `"...\n..."` 처럼 escape 돼서 나가므로, 원문 body 에서는 줄 단위로 안 보인다.
2. 파일 줄 `i` 와 view 줄 `j` 가 같으면, `(i-1, j-1)` 에서 끝난 run 을 이어 받는다(대각선으로 늘리기).
3. 규칙:
   - 줄은 앞뒤 공백을 빼고 비교 (들여쓰기·CRLF 차이 무시)
   - `}` / `return;` 같은 **사소한 줄은 run 을 시작 못 한다** — 어느 파일에나 있으니 증거가 안 됨
   - 의미 있는 줄이 **2개 이상** 이어져야 인정
   - 파일 읽기 도구가 붙이는 줄번호(`     1→code`)는 view 의 60% 이상이 그 모양일 때만 떼고 비교

### (C) "봤다" 와 "읽었다" 는 다르다
| 이 도구가 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|
| 이 파일의 1–4줄이 요청 #1 의 `$.messages[0].content[0].content` 안에 있었다 | 어느 프로세스가 그 파일을 열었는지 |
| canary 가 요청 #3 에 있었다 | 서버가 그 내용을 어떻게 썼는지 |
| 어떤 canary 는 캡처된 어떤 body 에도 없었다 | 캡처 밖(QUIC, 프록시 무시, body 한도 밖)으로 나간 게 없다는 것 |

"어느 프로세스가 읽었나" 까지 가려면 파일 I/O 추적(macOS `fs_usage`, Windows ETW / Process Monitor)이 필요하다. 다음 단계 후보.

## 3. 🟡 v11 에 없는 것 (본체 `provenance.js` 에는 있음)

| 부분 | v11 | 본체 |
|---|---|---|
| gzip/deflate body | 안 풂 | 풂 |
| SSE 스트림 | 원문만 | 이벤트별 + 같은 필드 이어붙이기 |
| base64 첨부, multipart | 원문만 (canary 는 바이트 그대로라 찾음) | 풀어서 별도 view |
| 바이너리 파일 | 건너뜀 | 바이트 그대로 / 최장 앞부분 |
| 문장 안에 인용된 긴 줄 | 못 찾음 | fragment 일치 |
| 중복 정리 | 없음 | 같은 body·같은 구간은 가장 구체적인 위치 하나만 |
| 커버리지 % | 없음 | 파일별 본 줄 수 / 의미 있는 줄 수 |
