## 2. ★ 꼭 이해하고 갈 것

### (A) 연결 key = 정렬한 endpoint 쌍
- `10.0.0.1:50000 | 10.0.0.2:80` — 양 방향 패킷이 같은 key.
- v1 이 Flow 에 기록한 `endpoints` 와 **같은 모양**. 본체에서 요청 → "Packets" 탭으로 내려가는 연결 고리가 이것.
- 한계: 같은 4-tuple 이 나중에 재사용되면(포트 재사용) 하나로 합쳐진다.

### (B) 순서번호는 '바이트 번호'
- seq = 이 세그먼트 첫 바이트의 번호. 다음 세그먼트 seq = 이전 seq + 이전 payload 길이.
- SYN, FIN 은 데이터가 없어도 번호 1개를 소비한다 → 상대 번호 기준점은 `ISN + 1`.
- ISN 은 보안상 랜덤 → 절대값 비교는 의미 없음.

### (C) 캡처에서 보이는 세 가지 이상 상황
| 표시 | 뜻 | 테스트 파일에서 |
|---|---|---|
| out of order | 뒤 바이트가 앞 바이트보다 먼저 도착 | #4(Host 줄)가 #5(요청줄)보다 먼저 |
| retransmission | 이미 받은 범위가 또 옴 | #7 = #6 재전송 |
| GAP | 순서번호가 건너뜀 = **캡처가 그 바이트를 못 봤다** | `Content-Length` 줄 21바이트 |

- GAP 을 0x00 이나 추측으로 채우지 않는다. 화면에 `«21 bytes missing»` 그대로.
- GAP ≠ 네트워크 손실. 실제로 잃은 바이트면 TCP 가 재전송하므로 받는 앱은 결국 다 받는다. GAP 은 "우리 캡처 지점에서 못 본 것" (드라이버 drop, 필터, 캡처 시작 전 등).

### (D) 왜 프록시 기록과 같이 봐야 하나
- 프록시(v1~v3)는 앱 관점의 '완성된' 요청을 본다. 패킷은 전송 과정의 '조각'을 본다.
- 둘을 같은 key 로 묶으면: "이 요청이 실제로는 패킷 몇 개, 재전송 몇 번, 몇 ms 에 걸쳐 갔나" 를 같이 볼 수 있다.

## 3. 🟡 안 한 것

- SACK, window/zero-window, 혼잡제어 해석
- 연결 재사용 분리, wrap 여러 번 (int32 차이로 한 번까지만)
- IPv6 확장 헤더가 끼어 있는 TCP (건너뜀)
